# voice-interrupt-loop

A real-time voice loop — VAD → STT (faster-whisper small) → reply → TTS — with **barge-in**: when the user talks over the assistant, TTS stops. The repo measures interruption latency p50/p95 on a labelled test set and shows the failure that most barge-in demos skip: **a speech VAD fires on the assistant's own voice (echo)** unless echo is handled.

## Why
Barge-in is what makes a voice agent feel like a conversation instead of a walkie-talkie. It needs two things at once: low latency from user onset to TTS stop, and **zero** false stops caused by the assistant hearing itself through the speaker. You cannot judge either without ground-truth onsets and echo in the test audio.

## Architecture
```mermaid
flowchart LR
  MIC[Mic frames<br/>16 kHz] --> SUB[Echo reference subtraction<br/>mic − ĝ·TTS ref]
  SUB --> VAD{VAD<br/>silero / webrtc / energy}
  VAD --> DTD{Double-talk gate<br/>RMS(residual) > 0.5·ĝ·RMS(ref) + floor}
  DTD -->|≥60 ms speech while SPEAKING| BI[Barge-in: stop TTS]
  DTD -->|speech then 500 ms silence while LISTENING| EP[Endpoint]
  EP --> STT[faster-whisper small<br/>int8 CPU] --> RP[Reply<br/>canned stub] --> TTS[macOS say] --> SPK[Speaker / TTSPlayer]
  SPK -. echo .-> MIC
  BI --> LIS[LISTENING<br/>interrupting speech kept as next turn]
```

## How it works
- [`voiceloop/vad.py`](voiceloop/vad.py) — streaming VADs with one interface: Silero (ONNX, 32 ms frames), WebRTC (aggressiveness 3, 30 ms), and an energy baseline.
- [`voiceloop/bargein.py`](voiceloop/bargein.py) — `BargeInDetector` streams the mic while TTS plays. Echo modes: `none`; `ref_sub` (subtract the known TTS signal with an estimated gain — a crude stand-in for AEC); `ref_sub_dtd` (ref_sub + a double-talk energy gate). Fires after 60 ms of consecutive speech frames.
- [`voiceloop/loop.py`](voiceloop/loop.py) — frame-driven state machine LISTENING → THINKING → SPEAKING → (barge-in) → LISTENING.
- [`voiceloop/stt.py`](voiceloop/stt.py) — faster-whisper wrapper (endpointed transcription, not token streaming) and WER.
- [`scripts/make_test_audio.py`](scripts/make_test_audio.py) — builds the test set.

### Test set (SYNTHETIC)
42 clips built with macOS `say` voices, not human recordings ([`data/manifest.json`](data/manifest.json)): 36 positives (6 interrupt phrases × 6 voices, paired, × echo at −12 / −20 dB) where the user starts 0.8–3.0 s into an assistant answer (Samantha voice), plus 6 echo-only negatives. Echo has a 40 ms delay; white noise at −50 dBFS. Ground-truth onset = first energetic 10 ms frame of the clean user clip. Audio is regenerated by the script (gitignored).

**Latency definition:** end of the frame where barge-in fired − ground-truth onset, plus the measured compute time of that frame. Output-device buffer latency (typically tens of ms) is **not** included.

## Results
From [`results/interrupt_latency.json`](results/interrupt_latency.json) (Apple M2 Pro, CPU):

| VAD | Echo handling | Detected (of 36) | False barge-ins (positives / echo-only) | Latency p50 | Latency p95 | VAD compute per frame p50 |
|---|---|---|---|---|---|---|
| silero | none | 0 | 36 / 6 of 6 | – | – | 0.20 ms |
| silero | ref_sub | 0 | 36 / 6 of 6 | – | – | 0.18 ms |
| **silero** | **ref_sub + DTD** | **36** | **0 / 0** | **62.0 ms** | **129.1 ms** | 0.17 ms |
| webrtc | none | 0 | 36 / 6 of 6 | – | – | 0.009 ms |
| webrtc | ref_sub + DTD | 36 | 0 / 0 | 70.9 ms | 170.1 ms | 0.025 ms |
| energy | ref_sub | 36 | 0 / 0 | 67.8 ms | 170.6 ms | 0.014 ms |
| energy | ref_sub + DTD | 36 | 0 / 0 | 67.8 ms | 177.4 ms | 0.016 ms |

Reading:
- **Without echo handling every VAD stops the assistant on its own voice**, in all 42 clips. Silero and WebRTC are designed to detect speech at any level, so even the residual left by imperfect subtraction (gain estimated at 0.8× true) still triggers them.
- A **double-talk gate** (the residual must carry clearly more energy than leftover echo could) fixes it: 36/36 detected, 0 false barge-ins. Silero gives the best p95 (129 ms).
- 60 ms of the latency is the deliberate debounce (`min_speech_ms`); the rest is VAD onset lag on soft word starts.
- **Tuning disclosure:** the gate's noise floor was raised once (0.003 → 0.01, i.e. ~10 dB above the noise) after a first run on this same set, so these numbers are in-sample.

### STT
From [`results/stt_small.json`](results/stt_small.json): faster-whisper small, int8, CPU, on the 36 interrupt utterances after reference subtraction: **mean WER 0.011**, 34/36 exact (the 2 misses: "can you repeat" → "do you repeat"). Latency p50 2943 ms / p95 6823 ms, **measured while a DPO fine-tune was running on the same machine**, so these latencies are inflated and should not be quoted as this model's speed. Re-run `python scripts/bench_stt.py` on an idle machine.

### End-to-end demo
[`results/demo_loop.json`](results/demo_loop.json): one scripted turn ("What is the plan for tomorrow?") → STT → canned reply → TTS → user says "Wait, stop." 2 s into the answer. Barge-in fired **64 ms** after onset (simulated sample clock); the interruption was transcribed as "wait and stop". STT/TTS compute times in that file were also measured under the same CPU contention.

## Limits
- Synthetic TTS voices, simulated echo (fixed gain/delay) and white noise — not a real room, speaker or microphone. Real AEC (e.g. WebRTC AEC3, Speex) is not implemented; `ref_sub` assumes the echo delay is known.
- The loop runs on recorded/simulated audio; a live mic/speaker mode is **not** built.
- STT is endpointed (transcribe after silence), not token streaming.
- The reply step is a canned stub, not an LLM.
- **Vision input: skipped.**
